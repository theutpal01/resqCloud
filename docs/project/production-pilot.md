# Production pilot configuration

## Current deployment

The application is deployed at [https://dsl9l1s4fdu1c.cloudfront.net](https://dsl9l1s4fdu1c.cloudfront.net) in AWS account `590951085792`, region `ap-southeast-2`, using the `resqcloud-prod` CLI profile. The infrastructure is defined in [`infra/aws/production.yaml`](../../infra/aws/production.yaml), and [`scripts/deployAwsProduction.mjs`](../../scripts/deployAwsProduction.mjs) builds, deploys, runs database bootstrap, and checks the public endpoints.

The current stack includes CloudFront, an HTTP-only origin connection to an internet-facing ALB, ECS Fargate API and web services (one task each), encrypted Aurora PostgreSQL with seven-day backups and deletion protection, Cognito, a private versioned evidence bucket, SQS with a dead-letter queue, SNS, ECR image scanning, CloudWatch logs, and Secrets Manager. Basic live checks have passed for `/`, `/health`, and `/ready`.

This is a limited technical pilot. HTTP between CloudFront and the ALB, one-task services, lack of a rehearsed disaster recovery plan, and the readiness gaps in [`status.md`](status.md) mean it is not approved for real emergency response or real personal/medical data.

For local development, use the [root `.env.example`](../../.env.example) as the safe template and never replace it with values copied from ECS. The template intentionally contains placeholders and optional settings, not production credentials. `NEXT_PUBLIC_*` values are public by design. AWS access keys are not application environment variables: the deploy operator uses the named AWS CLI profile, while production containers use the scoped ECS task role.

## Production URLs and API surface

The web app and API share the CloudFront origin. `/api/*`, `/health`, `/ready`, and `/socket.io/*` are forwarded to the API; other paths reach Next.js. Health endpoints are:

- `GET /health` — API process answers requests.
- `GET /ready` — API can connect to the database and find the migration table.

The versioned API is under `/api/v1`. It provides authentication and sessions, jurisdiction/department catalogs, public incident list and tracking, incident reporting and operations, responder assignments, notifications, analytics, administration/audit functions, and evidence-media operations. The detailed route and authorization inventory is in [`../engineering/api-reference.md`](../engineering/api-reference.md).

The current application pages include `/privacy`, `/auth/callback`, and role-aware workspace routes: `/` (overview), `/incidents`, `/report`, `/tracking`, `/map`, `/assignments`, `/escalations`, `/analytics`, `/notifications`, `/users`, `/departments`, `/jurisdictions`, `/audit`, `/settings`, and `/profile`. Access to workspace pages is role-gated. The privacy page is an interim product notice; retention, legal basis, controller, and contact details still need approval. There are no public pilot-scope, contact, or service-status pages. API health and readiness endpoints remain available for operational checks.

## Missing pages and capabilities

The current implementation inventory and planned work are tracked in [`feature-map.md`](feature-map.md), [`implementation-plan.md`](implementation-plan.md), and [`status.md`](status.md). The following user-facing and operational areas remain incomplete:

- Approved privacy/retention policy details; an interim privacy information page is available, but it is not a legal policy.
- Historical uptime reporting and active checks for Cognito, notifications, evidence delivery, and the map provider.
- Verification and activation of the proposed support email, support ownership, staffed hours, response expectation, and a backup contact channel.
- Jurisdiction selection and hierarchical state-to-district incident visibility are implemented. Admins can create and activate districts and assign authorities to active districts; reports route by the reporter-selected area. Verified district boundaries, coordinate-based jurisdiction inference, participating-agency validation, and approved production coverage remain incomplete.
- Authority MFA enrollment and recovery, account recovery, and safe provisioning. Application-level TOTP encryption is implemented, but its key migration and Secrets Manager configuration have not been deployed or verified in the live stack.
- Admin-only operational policy settings control accepted report categories, category-to-department routing, and high/critical first-response targets. Targets feed analytics; category mappings are validated against existing departments.
- Map pin selection, responder layers, routes, coverage, and heatmaps.
- Notification delivery preferences and complete email/SMS/push subscription management.
- Evidence malware/signature scanning, quarantine, cleanup, and previews.
- Signed CloudFront delivery for private evidence; the current `CLOUDFRONT_*` signer configuration is absent from the API task.
- Offline attachment sync and conflict resolution.
- Distributed rate limiting, WebSocket fan-out, and worker coordination for multiple tasks.

Do not present an AWS resource, API route, or health response as evidence that one of these product capabilities is complete.

## Deployment checks and operational gaps

Before each deployment, check the caller identity against the intended AWS account, inspect the CloudFormation change set, ensure migrations are reviewed, and verify `/`, `/health`, and `/ready` after rollout. The deployment script does not delete the former demo database; any retirement must be planned separately with a verified backup and explicit operator action.

Production readiness still requires HTTPS from CloudFront to the origin, multi-task behavior and rolling-deploy verification, security and privacy review, Aurora/PostgreSQL integration coverage, role-complete browser coverage, load and failure-injection checks, monitoring/alert thresholds, backup restore validation, and a disaster-recovery rehearsal. See [`../engineering/disaster-recovery.md`](../engineering/disaster-recovery.md) and [`../engineering/monitoring.md`](../engineering/monitoring.md).
